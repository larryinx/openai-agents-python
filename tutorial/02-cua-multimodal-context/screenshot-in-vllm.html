截图在 vLLM 里的一生

一个自定义工具 schema 的 computer-use agent，用 OpenAI Agents SDK 驱动，连到 vLLM 上的 Kimi-K3、DeepSeek-V4.1-Flash 或 Qwen3.8。每一步工具都返回一张截图。这一页跟踪截图从 SDK 的请求体出发，变成一串占位 token、再变成视觉编码器输出的向量，最后落进 KV cache 的全过程，以及三层缓存各自在什么时候命中。

图片怎么进上下文占一段占位 token 的位置token id 都一样；输入向量来自视觉编码器，在进入 LLM 前覆盖到这些位置上
缓存三层，键都是图片哈希处理器缓存、编码器缓存、KV 前缀缓存；旧截图主要靠前缀缓存复用
Responses API 告诉你什么只有 cached_tokens前缀缓存命中的 token 数；处理器和编码器缓存只在服务端指标里
三个模型Qwen3.8 看不了截图它是纯文本模型；Kimi-K3 和 DeepSeek-V4.1-Flash 带视觉编码器

一条 4 次请求的轨迹，按比例画出来

任务：“在浏览器的搜索框里输入 vLLM 并回车”。模型依次调用 screenshot()、click()、type_text()，每个工具返回一张截图，最后一次请求给出回答。SDK 每一步都把完整历史重新发给 vLLM，所以第 k 次请求里有 k−1 张截图。每一行的长条按 token 数等比例绘制，下面的细条是 vLLM 前缀缓存的命中情况。

三层缓存

    

      

        
缓存在哪里键命中时省掉什么CUA 轨迹中何时命中

        
          
多模态处理器缓存
--mm-processor-cache-gb 4		API server 进程（P0，只存元数据）+ EngineCore 进程（P1，存张量），CPU 内存mm_hash = blake3(模型名, 原始图片字节)HF 图像预处理（resize、切 patch），以及通过 IPC 再传一遍像素张量每次请求重新发来的旧截图都会命中；只有最新一张未命中。base64 解码和哈希每次仍会执行

          
编码器缓存GPU worker 显存（encoder_outputs[mm_hash]），由 EngineCore 的 EncoderCacheManager 记账mm_hash视觉编码器（ViT）前向只在截图跨过前缀命中边界、需要重新算一部分时用到；请求结束后条目变成“可释放”但会保留，直到空间不够被淘汰

          
KV 前缀缓存
enable_prefix_caching=True		GPU 显存里的 KV 块，哈希表在 EngineCore链式块哈希：父块哈希 + 块内 token id + 块内每张图的 (mm_hash, 偏移)整段 prefill。完全落在命中区间里的截图，连编码器都不会被调度历史只追加不改写时，上一次请求的整段前缀都能命中；任何改写（删旧截图、改写历史 reasoning）都会让后面的块全部失效

Responses API 返回了什么

    

      

        
一次 CUA 步骤的 usage（示例数值）


{
  "input_tokens": 9876,        // 含全部截图的占位 token
  "input_tokens_details": {
    "cached_tokens": 8192,     // KV 前缀缓存命中，按块对齐
    "cache_write_tokens": 1680, // 本次新写入缓存的整块
    "input_tokens_per_turn": [],  // vLLM 扩展；这三个模型为空
    "cached_tokens_per_turn": []
  },
  "output_tokens": 57,
  "output_tokens_details": {
    "reasoning_tokens": 31,     // 需要 --reasoning-parser
    "tool_output_tokens": 0,
    "output_tokens_per_turn": [],
    "tool_output_tokens_per_turn": []
  },
  "total_tokens": 9933

怎么读

        
    
          
  • cached_tokens 在 Responses API 里总是返回，不需要任何启动参数；它等于本地前缀命中加上 KV connector 的外部命中。
    • 
          
  • 命中按整块计算，并且最多到 input_tokens − 1，所以它永远小于 input_tokens。
    • 
          
  • 截图的占位 token 也算在 input_tokens 和 cached_tokens 里，但响应里没有单独的图片 token 数。
    • 
          
  • 处理器缓存、编码器缓存的命中情况不会出现在任何响应里。要看它们，用 Prometheus 的 vllm:mm_cache_queries / vllm:mm_cache_hits（处理器缓存，按图片个数），或用 --enable-logging-iteration-details 看每一步实际送进编码器的图片数。
    • 
          
  • Chat Completions 要加 --enable-prompt-tokens-details 才返回 prompt_tokens_details，其中还有按模态统计的 multimodal_tokens。
    • 
          
  • Agents SDK 会把每一步的 cached_tokens 累加到 result.context_wrapper.usage；vLLM 的扩展字段用 ModelSettings(preserve_raw_usage=True) 从 raw_usage 读取。
    •

SDK 侧要做的选择

    

      

        
推荐做法

        
    
          
  • 用普通函数工具实现 click / type_text / screenshot，返回 ToolOutputImage。内置的 ComputerTool 需要模型输出 OpenAI 的 computer_call，vLLM 上的开源模型不会产生这种条目。
    • 
          
  • 用 OpenAIResponsesModel 连 vLLM 的 /v1/responses，截图会留在 function_call_output 里。
    • 
          
  • 给 ToolOutputImage 设置 detail="auto"。vLLM 校验工具结果里的 input_image 时要求有 detail，而 SDK 在它为空时不发送这个字段。
    • 
          
  • 让历史只追加不改写，前缀缓存才能覆盖旧截图。
    • 
        

      

      

        
容易踩的坑

        
    
          
  • OpenAIChatCompletionsModel 会丢掉工具结果里的图片：只有图片时替换成 [tool output omitted]，图文混合时图片被静默删除。要么换 Responses，要么用 call_model_input_filter 把截图挪到 user 消息里。
    • 
          
  • “只保留最近 N 张截图”的过滤器能控制上下文长度，但每次改写都会让前缀缓存从第一张被改写的截图处失效。
    • 
          
  • SDK 不会自动裁剪旧截图；RunState 序列化时每张截图的 base64 会出现 4 次，Session 也会保存完整 base64。
    • 
          
  • 多个 data parallel 引擎时，同一条轨迹的请求可能被路由到不同引擎而丢失缓存，可以用 X-data-parallel-rank 请求头固定。
    • 
        

      

    

  


  

    模拟中的文本长度是示意值：system + 工具 schema 2000、任务 100、每次模型输出 200、每个工具结果的文字 20 个 token。截图 token 数按 vLLM 中各模型的预处理规则计算。混合注意力模型的命中粒度依赖 TP、KV dtype 和后端，这里按 TP8、bf16 KV 的估算值。
